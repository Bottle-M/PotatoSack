# PotatoSack 3.0.0 设计

2026.9-10

## 1. 增量备份体积大幅优化

* 所有数值类型均按**大端序**存储

现有增量备份机制有明显问题: 对于 Minecraft 存档这种 MCAnvil (`.mca`) 体积占比很大的区域文件，就算玩家只动了一个方块，甚至没有动方块，仅仅是在区块附近导致区块的 `InhabitedTime` 等属性发生变动，可能**也要备份这一整个区域文件**，其实还是挺浪费空间的。  

针对这一点，在增量备份比较变动时，我们需要特殊处理 `.mca` 文件的变动比较，相对应的，备份记录文件 (`_备份路径标识.json`) 也需要有较大变化（需要记录更细节的 `.mca` 中区块内容的差别，因此**存储结构也需要变得更紧凑**）。

### 1.1. 备份记录文件格式

涉及 `.mca` 时需要存储每个区块的状态信息。存储和 NBT 一样，为了节省存储空间，需要设计更为紧凑的存储格式。

```
[ uint32 存储格式版本号 ] [ uint64 存储最后修改时间戳 ] [ uint64 文件数量 ] [ 文件最后修改时间表 ] [ 文件哈希表 ] [ 文件路径字符串长度表 ] [ 紧凑的文件路径字符串表 ] [ mca 数据部分，每个 .mca 文件一个 varint[1024] 的数组 ]
```

#### 主要字段说明

* **存储格式版本号** (`uint32`): 记录当前备份记录文件的格式版本，确保以后紧凑存储结构发生更改仍能做兼容。
* **最后修改时间戳** (`uint64`): 记录当前备份记录文件的最后修改时间戳。
* **文件数量** (`uint64`): 当前备份记录文件所存储的文件记录数。

**注 1**：文件路径字符串已经隐含了文件类型，可以用后缀名判断（Minecraft 本体也是靠后缀名来找到区域文件的），不需要额外的表来记录文件类型。  
**注 2**：有很多紧凑的表是**为了压缩率着想**，这样压缩算法更容易发现重复模式。

* **文件最后修改时间表** (`uint64[]`): 每条记录对应文件的最后修改时间拼接得到 (长度为文件数量)。
* **文件哈希表** (`uint64[]`): 每条记录对应文件的 XXH3_64 哈希拼接得到 (长度为文件数量)。
* **文件路径字符串长度表** (`uint16[]`): 每条记录对应的相对路径占用的字节数 (长度为文件数量)。
* **紧凑的文件路径字符串表** (`byte[]`): 根据**文件路径字符串长度表**存储指定长度的文件相对路径字符串。

根据文件路径字符串，我们能筛选出 `.mca` 文件，设有 `mcaLen` 个文件。然后在 `mca 数据部分` 中存储 `mcaLen` 个 `.mca` 文件的区块最后变更时间戳（即区域文件格式文件头的 4 KiB 区块时间戳），按照 `.mca` 出现的顺序存储：  

* **每个 `.mca` 文件一个 `varint[1024]` 的数组**: 存储每个区块的最后变更时间戳。这里用 varint 编码，因为可能一个 `.mca` 文件中不是所有区块都初始化了，**可能有很多区块的时间戳是 0**，使用 varint 编码可以大量节省空间。

持久化到硬盘上时，会**使用 ZStandard 压缩算法压缩**以进一步减小体积。  

### 1.2. MCAnvil 特殊存储处理 (PSMCA 格式, a.k.a. delta mca)

全量备份时 `.mca` 文件原样存储，而**增量备份时，`.mca` 文件只存储发生变动的区块**。  

增量备份时的 `.mca` 文件 delta 存储格式:  

```
[ MAGIC ] [ uint16 MCA Delta 文件版本 ] [ uint16 区块数量 ] [
    [ uint16 区块下标 (0..1023) ] [ uint8 区块占用扇区数 ] [ varint 区块最后变更时间戳 ] [ 区块数据 (长度: 扇区数 * 4 KiB) ]
    ...
]  
```

* **MAGIC**: 6 个字节 `PSMCA\x00`，用于标识增量备份的特殊 `.mca` 文件。`.mca` 文件自身**几乎不可能出现这个魔数**。  
* **MCA Delta 文件版本** (`uint16`): 记录当前增量备份 `.mca` 文件的格式版本，确保以后增量备份 delta `.mca` 文件格式发生更改仍能做兼容。
* **区块数量** (`uint16`): 记录当前增量备份 `.mca` 文件中存储的区块数量 (0..1024)，用于计算后续区块数据长度。

随后顺序存储每个区块的数据:  

* **区块下标** (`uint16`): 记录原 `.mca` 文件中此区块的下标 (0..1023)。
* **区块占用扇区数** (`uint8`): 和 `.mca` 中的区块扇区数量一致。记录原 `.mca` 文件中此区块占用的扇区数 (4 KiB 一个扇区)，用于计算区块数据长度。
  * 对于被删除 / 不存在的区块，占用扇区数**标记为 0**，**不存储区块数据**。
* **区块最后变更时间戳** (`varint`): 记录原 `.mca` 文件中此区块的最后变更时间戳，和 `.mca` 中的区块时间戳一致。
* **区块数据** (`byte[]`): 记录原 `.mca` 文件此区块的数据，长度为 `区块占用扇区数 * 4 KiB`，**带填充**。  

**注**： OneDrive 流式压缩上传时要保证 `.mca` 文件的**读取一致性**。

### 1.3. MCC 文件处理

`.mcc` 文件存储溢出指定扇区大小的**区块数据**，全量和增量备份中作为单独文件判断和备份即可。 

> 区块数据溢出时，这个区块在 `.mca` 文件头部存的 `起始扇区偏移 = offset`, `占用扇区数 = 1`；  
> 在 `.mca` 的 offset 这个扇区偏移处，存的是 hex(00 00 00 01 82 <padding>)，即数据长度为 1，压缩类型最高位置 1，游戏默认压缩类型是 2，因此这里是 0x82。有 padding 是因为要填充到 1 个扇区；  
> 这个时候，就会根据 `.mca` 文件名（区域坐标）和区块下标，计算出这个区块的实际坐标，找到对应的 `.mcc` 文件，读取这个区块的实际数据。  

也就是说就算额外有 `.mcc` 文件，`.mca` 中也有一个“存根”留着，完全可以复用 1.2 节的逻辑，不用管 `.mcc` 文件的内容。只要 `.mca` 文件的区块数据发生变动，`.mcc` 文件就会被备份。

### 1.4. 思考：区块时间戳和删除可能导致的问题  

首先，考虑一种情况，我们存的区块时间戳是秒级的，有没有可能出现 “区块 A 在**同一秒内**多次改了内容时间戳未变，而区块 B 时间戳变了，导致这次增量只备份 B” 的情况：  

1. MCAnvil 所有区块应该近乎是同时写入的，单次更新中，区块的时间戳通常会一起变化；
2. “区块 A 在同一秒内多次被更新” 的情况几乎不会出现。如果是流式备份，启动前就会暂停世界自动保存和退避。在这之后，区块 A **最多只可能意外被刷写一次**；如果是传统方式的备份，zipSpecificFilesUtil 也会做 mtime、大小、crc32 校验（当然流式备份也是有这些完整性校验的），确保文件在读取和加入压缩包过程中没有发生修改。

另外再考虑一种情况：某个**区块内容发生变化或者被删除**，但是时间戳没有发生变化，那么产生 delta mca 文件时就会漏掉这个区块。就删除而言，如果遗漏掉，delta mca 文件中就不会记录 “这个文件已经被删除”。  

关于这点，我的想法是，通常 Minecraft 服务端的正常行为是只要对区块进行了修改，必然会修改时间戳，而且游戏内区块自从被创建后只有变更一说，通常不考虑区块被删除的情况。就算被外部工具（如 MCA Selector）编辑或删除了且时间戳没有变，Minecraft 服务器启动后如果还会用到这区块，那么怎么样都是会重新生成这个区块的（一旦重新生成，这一块的时间戳必然发生变化），没有重新生成 / 发生变更的话，说明没有用到这个区块，那为什么要删除或者编辑它呢？  

就算这点真有影响，也仅限于**在某次全量备份后我用外部工具对世界进行了手动编辑**，仅仅影响一次全量备份后的增量备份。而全量备份通常相隔的时间也不会非常长，影响完全是有限的。  

因此为了降低打包时的运算量，我依旧使用区块时间戳是否变化作为是否加入 delta mca 的标准。如果后面实在有场景受到影响，那可以考虑给每个区块数据计算一个哈希值，在记录文件中存哈希而不是时间戳。
